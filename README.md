# پنل مدیریت کانفیگ روی Cloudflare Workers

<div dir="rtl">

پنلی تک‌فایل برای ساخت، مدیریت و توزیع کانفیگ‌های **VLESS / Trojan / Shadowsocks / VMess** روی لبه‌ی شبکه‌ی کلاودفلر — بدون سرور، بدون npm، بدون هزینه.

> **نام پروژه:** Panel Core • **نسخه:** 2.0.0 • **زبان:** JavaScript (Workers) • **رابط:** فارسی/RTL

---

## ✨ معرفی

این پروژه یک ورکر Cloudflare است که سه کار انجام می‌دهد:

1. **هسته‌ی تونل** — اتصال VLESS و Trojan روی WebSocket را واقعاً می‌پذیرد و ترافیک را با `cloudflare:sockets` به مقصد می‌رساند.
2. **پنل مدیریت** — رابط کاربری کامل (تک‌صفحه‌ای، فارسی، تم تاریک/روشن) که **از گیت‌هاب خوانده می‌شود** (مثل نهان): فایل‌های `ui/index.html`، `ui/style.css`، `ui/app.js`.
3. **سرویس اشتراک** — لینک ساب‌اسکریپشن با ۶ فرمت خروجی و تشخیص خودکار کلاینت.

### چرا این معماری؟
فایل‌های UI جدا از موتور هستند؛ یعنی می‌توانید ظاهر پنل را عوض کنید **بدون دست زدن به ورکر** — کافی است فایل‌های css/html را در مخزن گیت‌هاب تغییر دهید (قابلیت **FR** در تنظیمات).

## 🚀 نصب

### روش ۱ — داشبورد کلاودفلر با نسخهٔ ضد-1101 (توصیه‌شده)

> **چرا این روش؟** فایل `worker.js` خام، رشته‌های پروتکل (`vless`، `trojan` و…) را به‌صورت متن ساده دارد و می‌تواند اسکنر استاتیک کلاودفلر را فعال کند (نتیجه: خطای ۱۱۰۱ یا محدودسازی حساب). نسخهٔ obfuscate شده هیچ رشتهٔ پروتکلی ندارد — همان روشی که پروژه‌های مثل byJoey/cfnew استفاده می‌کنند.

**گام ۱ — ساخت نسخهٔ obfuscate شده:**

```bash
npm install
npm run build
```

خروجی: فایل **`_worker.obf.js`** (حدود ۵ مگابایت). این فایل نسخهٔ امن و قابل‌دیپلوی است — و **از قبل ساخته‌شده در همین مخزن** هم موجود است؛ اگر نمی‌خواهید Node اجرا کنید، همان فایلِ موجود در ریپو را بردارید.

**گام ۲ — دیپلوی در داشبورد:**

1. وارد <https://dash.cloudflare.com> شوید
2. **Workers & Pages → Create application → Create Worker**
3. نام را `panel` بگذارید → **Deploy**
4. روی ورکر کلیک کنید → **Edit code**
5. کل محتوای ادیتور را پاک کنید و **تمام فایل `_worker.obf.js`** را جایگذاری کنید (`Ctrl+A` → `Ctrl+V`)
6. **Deploy** را بزنید و آدرس `https://panel.<account>.workers.dev` را باز کنید

> رمز پیش‌فرض: **`simorgh`**

> ⚠️ **نکتهٔ obfuscation:** چون کد obfuscate شده، اشکال‌زدایی (debug) سخت است. برای عیب‌یابی، موقتاً فایل `worker.js` خام را پیست کنید، مشکل را پیدا و رفع کنید، بعد دوباره `npm run build` بزنید.

### روش ۲ — داشبورد کلاودفلر با نسخهٔ خام (فقط برای عیب‌یابی)

همان مراحل روش ۱، ولی فایل [`worker.js`](./worker.js) را جایگذاری کنید. **توصیه نمی‌شود** — رشته‌های پروتکلِ خام ممکن است پرچم بخورد.

### مرحله‌ی مهم: بارگذاری UI از گیت‌هاب

رابط کاربری از گیت‌هاب خوانده می‌شود:

1. یک مخزن بسازید و چهار فایل پروژه را در آن بگذارید:
   ```
   ui/index.html
   ui/style.css
   ui/app.js
   ```
2. در پنل وارد شوید → **پروتکل و کانفیگ → Fragment و FR**
3. مقدار `fr.repo` را به `username/repo` تغییر دهید و ذخیره کنید
4. صفحه را رفرش کنید (دکمه‌ی «بازخوانی» در **تنظیمات و پشتیبان → فایل‌های UI**)

> اگر گیت‌هاب در دسترس نباشد، ورکر پیام «بارگذاری رابط کاربری ناموفق بود» نشان می‌دهد. برای تست محلی می‌توانید فایل‌ها را در مخزن خودتان میزبانی کنید.

### مرحله‌ی مهم‌تر: ذخیره‌سازی پایدار (KV)

بدون KV، کاربران و تنظیمات با سرد شدن ورکر **ریست می‌شوند**:

از داشبورد: **Worker → Settings → Bindings → Add → KV Namespace → Variable name: `KV`**

(اگر قبلاً wrangler داشتید: `npx wrangler kv namespace create KV_PERSIST` — ولی برای این روش، داشبورد کافی است.)

متغیرهای اختیاری:

| متغیر | توضیح |
|---|---|
`MASTER_KEY` | رمز ورود پنل (بر ترتیب اولویت از تنظیمات داخلی) |

## 🧭 استفاده

### ۱) ساخت کاربر
**کاربران → کاربر جدید** → نام، سهمیه و انقضا را بدهید. UUID و رمز خودکار ساخته می‌شوند.

هر کاربر می‌تواند تنظیمات اختصاصی داشته باشد: حالت (Alpha/Beta/Both)، پورت‌ها، IPهای پاک، Proxy IP، Node، NAT64، Panel URL، محدودیت اتصال/IP/کانفیگ، سرعت و بلاک محتوا.

### ۲) گرفتن لینک ساب
**اشتراک** → کاربر را انتخاب کنید → کپی لینک یا QR.

```
https://panel.<account>.workers.dev/sub/<uuid>
```

| کلاینت | فرمت خودکار |
|---|---|
v2rayNG / v2rayN / Shadowrocket | Base64
Hiddify / Karing / Happ / Sing-box | Sing-box JSON
Clash Meta / Mihomo / FlClash | Clash Meta JSON
Clash | YAML
V2RayN (JSON) | V2Ray JSON |

تحمیل صریح فرمت: `?format=base64|raw|clash|meta|singbox|v2ray`

### ۳) افزودن کاربر در کلاینت
- **v2rayNG:** آیکون + → «کپی از کلیپ‌بورد» (لینک ساب را کپی کنید) → آیکون ⋮ → «به‌روزرسانی اشتراک»
- **Hiddify:** افزودن پروفایل → «لینک اشتراک» را بچسبانید
- **Clash Meta:** Profiles → لینک را وارد کنید

### ۴) صفحه‌ی وضعیت کاربر
```
https://panel.<account>.workers.dev/status/<username>
```
مصرف، باقیمانده و تاریخ انقضا را بدون ورود نشان می‌دهد.

## 🛰 اسکنر آی‌پی تمیز (رادار)

در پایین صفحه‌ی کاربر یک کارتِ **رادار آی‌پی تمیز** هست که کاملاً در مرورگر اجرا می‌شود: رنج‌های رسمیِ کلودفلر را می‌گردد، آی‌پی‌های زنده را پیدا می‌کند و بر اساس پینگ مرتب می‌کند، بعد آن‌ها را در پنل ذخیره و روی کانفیگ‌های همان کاربر اعمال می‌کند.

**تنظیمات:** پنل → **پیکربندی → اسکنر آی‌پی**

| تنظیم | پیش‌فرض | توضیح |
|---|---|---|
`enabled` | روشن | نمایش/پنهان‌کردن کارت اسکنر در صفحه‌ی کاربر |
`ipCount` | **۲۰۴۸** | تعداد آی‌پی‌های هر اسکن |
`concurrency` | **۱۶** | تعداد پروب‌های موازی (بالاتر = سریع‌تر، ولی فشارِ بیشتر روی شبکه) |
`timeout` | **۲۰۰۰ ms** | تایم‌اوت هر پروب — زیرِ ۱۵۰۰ms روی شبکه‌ی موبایل خیلی از لبه‌های سالم «مرده» حساب می‌شوند |
`probes` | **۳** | تعداد پروب برای تأییدِ هر آی‌پی (میانگین + لرزش + افت) |
`autoFloor` | **روشن** | کفِ خودکارِ تأخیر — تأخیرِ پایه تا دامنه‌ی ورکر اندازه‌گیری می‌شود و پاسخ‌های بی‌درنگ (RSTِ فیلترشکن/میان‌راه) رد می‌شوند. **همین تنظیم است که «آی‌پی پیدا می‌شود ولی در کانفیگ کار نمی‌کند» را رفع می‌کند** |
`minRtt` | ۰ | کفِ دستیِ تأخیر — ۰ = فقط کفِ خودکار. اگر در نتیجه پاسخ‌های بسیار سریع (زیر ۲۰ms) می‌بینید، اینجا مقدار بگذارید |
`maxRtt` | ۰ | حداکثر تأخیرِ قابل‌قبول — ۰ = بدون سقف |
`keep` | ۰ | تعداد آی‌پیِ ذخیره‌شده — ۰ = سقفِ کانفیگِ کاربر |
`mode` | `smart` | `smart` = سهمِ متناسب با اندازه‌ی رنج + کفِ تضمینی برای هر رنج • `even` = سهمِ برابر برای هر رنج • `random` = تصادفیِ وزنی |
`ports` | خالی | پورت‌های اسکن — خالی = پورت‌های TLS خودِ کانفیگ‌های کاربر (و اگر پیدا نشد، ۴۴۳) |
`ranges` | خالی | رنج‌های CIDR دلخواه — **به** فهرست رسمی اضافه می‌شوند |

### رنج‌های اسکن‌شده
همیشه **تمامِ** رنج‌های رسمیِ IPv4 کلودفلر (مستقیماً از <https://www.cloudflare.com/ips-v4>) اسکن می‌شوند — نه زیرمجموعه و نه بازه‌ی دستی:

```
173.245.48.0/20    103.21.244.0/22   103.22.200.0/22   103.31.4.0/22
141.101.64.0/18    108.162.192.0/18  190.93.240.0/20   188.114.96.0/20
197.234.240.0/22   198.41.128.0/17   162.158.0.0/15    104.16.0.0/13
104.24.0.0/14      172.64.0.0/13     131.0.72.0/22
```

### اجرای اسکن از خودِ پنل
لازم نیست صفحه‌ی کاربر را باز کنید: در **پیکربندی → اسکنر آی‌پی** کارتِ **اجرای اسکن از پنل** هست.

- **شروع اسکن / توقف** — با نوارِ پیشرفت و شمارنده‌ی زنده‌ی آی‌پی‌های سالم.
- **جدولِ نتیجه:** آی‌پی:پورت • تأخیر • لرزش • افت — مرتب‌شده بر اساس بهترین امتیاز.
- **اعمال و ذخیره در «IPهای پاک»** — آی‌پی‌های برتر اولِ فهرستِ `cleanIPs` می‌نشینند (بدون تکرار، سقف ۱۰۰) و همان لحظه ذخیره می‌شوند.
- مقادیرِ **همین صفحه** استفاده می‌شوند (تعداد، هم‌روندی، تایم‌اوت، پورت‌ها، رنج‌ها) — لازم نیست اول ذخیره کنید تا یک اسکنِ آزمایشی بگیرید.
- پروب از مرورگرِ خودتان انجام می‌شود، پس نتیجه همان چیزی است که کاربرانتان می‌بینند.

### چطور کار می‌کند
- **پروبِ دوکاناله (`Image` + `fetch`) —** روی `https://<ip>:<port>/cdn-cgi/trace`. گواهیِ آی‌پیِ خام هیچ‌وقت معتبر نیست، پس مرورگر بعد از TLS اتصال را رد می‌کند و «سرعتِ رسیدنِ خطا» خودش سیگنالِ زنده‌بودنِ لبه است:
  - خطا **پیش از** تایم‌اوت = لبه پاسخ داد = **سالم**
  - **تایم‌اوت** = هیچ پاسخی نیامد = **مرده**

  هر دو کانال **موازی** فرستاده می‌شوند و اولین سیگنال برنده است. چرا هر دو: تجربه‌ی عملی نشان داده هیچ‌کدام به‌تنهایی قابل‌اعتماد نیست —
  - نسخه‌ی اصلیِ همین پنل اول `Image` داشت و بعد به `fetch` مهاجرت کرد، چون «RST آنیِ فیلترشکن/مسیرِ مسدود هم زنده حساب می‌شد».
  - پنل [نوا](https://github.com/norayanmostafa/nova) برعکس، `fetch` را رها کرد و به `Image` رفت.
  - اسکنرِ [IRCF](https://ircfspace.github.io/tester/) با `fetch` و اسکنرِ [SenPai](https://github.com/MatinSenPai/SenPaiScanner) با Go کار می‌کنند.

  اگر یکی از دو کانال در مرورگر/شبکه‌ی کاربر از کار بیفتد، دیگری اسکن را نجات می‌دهد و نتیجه بی‌صدا خالی نمی‌ماند.
- **کفِ تأخیر — مهم‌ترین فیلترِ کیفیت:** پیش از هر اسکن، یک درخواستِ کامل به **دامنه‌ی خودِ ورکر** زده می‌شود. این دامنه روی کلادفلر است، پس تأخیرِ اندازه‌گیری‌شده یک «لبه‌ی واقعی» است. سپس هر پاسخی که **بسیار سریع‌تر** از آن باشد رد می‌شود (`کف = max(۲۰ms, ۴۰٪ تأخیرِ پایه)` با سقفِ ۲۰۰ms).
  چرا حیاتی است: `RSTِ` آنیِ فیلترشکن/میان‌راه در حدودِ ۱ms می‌رسد و بدونِ این کف، رتبه‌بندیِ «سریع‌ترین اول» باعث می‌شود **آی‌پی‌های خراب جای آی‌پی‌های سالم را در کانفیگ بگیرند** — یعنی «آی‌پی پیدا می‌شود ولی در کانفیگ کار نمی‌کند». تعدادِ رد‌شده‌ها در خطِ وضعیت (`مردودِ سریع`) و در پنل دیده می‌شود.
- **دروازه‌ی ثبات:** آی‌پی‌ای که از `probes` پروب فقط یک‌بار پاسخ بدهد پذیرفته نمی‌شود (حداقل ۲ پاسخ لازم است). لبه‌ی واقعی هر بار پاسخ می‌دهد؛ مسیرِ نیمه‌باز (که DPI بعد از اولین درخواست می‌بندد) نه.
- **پورت‌ها موازی** آزموده می‌شوند تا یک آی‌پیِ مرده فقط **یک** تایم‌اوت هزینه بدهد؛ پروب‌های تکمیلی فقط برای پورتِ برنده اجرا می‌شوند (میانگین، لرزش، افت، امتیاز = `avg + jitter×0.5 + loss×20`). فقط پورت‌های TLS (۴۴۳ • ۲۰۵۳ • ۲۰۸۳ • ۲۰۸۷ • ۲۰۹۶ • ۸۴۴۳) معنی دارند — پورتِ غیر-TLS با خطای SSL بی‌درنگ «پاسخ» می‌دهد و همه‌چیز را زنده نشان می‌دهد.
- **فاصله‌ی تصادفیِ ۱۰ تا ۶۰ میلی‌ثانیه** بین پروب‌های یک آی‌پی — الگوی درخواست‌ها کمتر شبیه اسکنر می‌شود و DPI کمتر اتصال را قطع می‌کند (روشِ [SenPai Scanner](https://github.com/MatinSenPai/SenPaiScanner)). همین چند پروب هم افتِ بعد از اولین درخواست (که روی ISPهای ایران رایج است) را نشان می‌دهد.
- **خودآزماییِ پروب:** پیش از هر اسکن، پروب روی سه آی‌پیِ آزمایشیِ RFC 5737 (`192.0.2.1` • `198.51.100.1` • `203.0.113.1`) اجرا می‌شود. این بازه‌ها هرگز مسیریابی نمی‌شوند، پس اگر پروب به آن‌ها «پاسخ» بدهد یعنی هر خطای سریعِ محلی دارد «زنده» تفسیر می‌شود و نتیجه بی‌اعتبار است — در آن حالت هشدار داده می‌شود. (کفِ خودکارِ تأخیر معمولاً همین مشکل را خودکار خنثی می‌کند؛ `minRtt` فقط برای سخت‌گیریِ دستیِ بیشتر است.)
- **شمارنده‌ی پاسخ:** وضعیتِ اسکن تعدادِ «پاسخ‌های خام» را جدا از تعدادِ آی‌پی‌های پذیرفته‌شده نشان می‌دهد. اگر اسکن با صفر نتیجه تمام شود، پیام تفکیک می‌کند: «هیچ آی‌پی پاسخ نداد» (شبکه اتصالِ مستقیم TLS به آی‌پیِ خام را می‌بندد) در مقابل «پاسخ آمد ولی فیلتر شد» (`minRtt`/`maxRtt`).
- **تخصیصِ بودجه (`smart`):** سهمِ هر رنج به‌تناسبِ اندازه‌اش است، با یک کفِ تضمینی تا رنج‌های کوچک هم اسکن شوند. دلیل: در فهرست‌های عمومیِ آی‌پیِ تمیز، حدود **۹۶٪** آی‌پی‌های سالم در ۳ رنجِ بزرگ (`104.16.0.0/13` • `172.64.0.0/13` • `104.24.0.0/14`) هستند و **۹ رنجِ دیگر تقریباً هیچ آی‌پیِ سالمی ندارند**. حالتِ `even` حدود ۸۰٪ بودجه را خرجِ همان ۹ رنج می‌کرد؛ `smart` در ۲۰۴۸ نمونه ~۸۳٪ بودجه را به ۳ رنجِ پربازده می‌دهد (در مقابل ~۲۰٪ برای `even`) و هیچ رنجی را صفر نمی‌گذارد.
- **ذخیره:** آی‌پی‌های برتر با `POST /<sub-path>/<user-id>/radar-ips` ذخیره می‌شوند — روی کانفیگ‌های همان کاربر و در «شبکه ← IPهای پاک» پنل.
- **لاگ:** هر اسکن (موفق یا بی‌نتیجه) در **لاگ → رادار** ثبت می‌شود.

### محدودیتِ ذاتیِ اسکنِ مرورگری
مرورگر نمی‌تواند SNI را برای یک آی‌پیِ خام تعیین کند و گواهیِ آی‌پی هم معتبر نیست، پس **نمی‌توان بدنه‌ی `/cdn-cgi/trace` را خواند یا `CF-Ray`/`colo` را دید**. یعنی اسکنِ مرورگری فقط می‌تواند بگوید «روی این آی‌پی در یک رنجِ رسمیِ کلودفلر، سرویسِ TLS پاسخ داد» — نه اینکه «این دقیقاً یک لبه‌ی کلودفلر است».

> **مهم — چرا روی بعضی شبکه‌ها نتیجه صفر است:** پروبِ مرورگری TLS را **بدون SNI** می‌فرستد (آی‌پیِ خام). روی شبکه‌های ایران، DPI اغلب دقیقاً همین الگو را می‌بندد، در حالی که اتصالِ واقعیِ پروکسی (با SNI درست) سالم کار می‌کند. نتیجه: آی‌پی‌ها واقعاً کار می‌کنند ولی اسکنرِ همان دستگاه پیدایشان نمی‌کند. **راه‌حل: اسکن را از یک VPS/شبکه‌ی تمیز انجام دهید** — یا از کارتِ «اجرای اسکن از پنل» استفاده کنید. اگر `timeout` را بالا ببرید و همچنان شمارنده‌ی «پاسخ» صفر بماند، همین محدودیت است، نه خرابیِ اسکنر.

این برای هدفِ ما کافی است (رنج‌ها از پیش فقط کلودفلر هستند)، ولی اگر اعتبارسنجیِ قطعی می‌خواهید، [SenPai Scanner](https://github.com/MatinSenPai/SenPaiScanner) همین کار را بومی (با Xray و خواندن `colo`) انجام می‌دهد.

> تست بدون مرورگر: `node tests-manual/scanner-engine.cjs` (موتورِ صفحه‌ی کاربر) و `node tests-manual/panel-scanner.cjs` (اسکنرِ داخلِ پنل) و `node tests-manual/worker-e2e.cjs` (e2e ورکر + فالبک‌ها)

## 🔧 عیب‌یابی: «کانفیگ وصل نمی‌شود»

به‌ترتیب این موارد را بررسی کنید:

| مشکل | راه‌حل |
|---|---|
**SNI/Host اشتباه** | در **پروتکل و کانفیگ** فیلدهای `SNI` و `Host` را **خالی** بگذارید تا دامنه‌ی خود ورکر استفاده شود. اگر مقداری مثل `discordapp.com` باشد، کلاودفلر ترافیک را به سایت دیگری می‌فرستد و کانفیگ کار نمی‌کند.
**دامنه‌ی workers.dev فیلتر است** | به ورکر یک **دامنه‌ی اختصاصی** وصل کنید (Settings → Domains & Routes) و همان دامنه را در فیلد SNI بگذارید، یا از Clean IP به‌عنوان آدرس + دامنه‌ی خودتان به‌عنوان Host استفاده کنید.
**پروتکل خاموش است** | در تنظیمات، VLESS یا Trojan روشن باشد؛ اگر Shadowsocks/VMess فعال است بدانید که این دو در هسته‌ی تونل پیاده نشده‌اند (فقط در ساب تولید می‌شوند) — برای اتصال واقعی از VLESS یا Trojan استفاده کنید.
**UDP لازم دارید** | هسته‌ی فعلی فقط TCP را تونل می‌کند (دانلود و وب‌کامل کار می‌کند، بعضی بازی‌ها/تماس‌ها نه).
**مقصد فیلتر است** | در تنظیمات `Proxy IP` را پر کنید؛ خروجی از طریق آن relay می‌شود.
**Panic Mode فعال است** | دکمه‌ی قرمز `Panic` در نوار بالا را خاموش کنید.
**کاربر منقضی/غیرفعال** | در بخش کاربران وضعیت و سهمیه را بررسی کنید.

تست سلامت: `https://panel.<account>.workers.dev/health`

## ⚠️ محدودیت‌ها و نکات

- هسته‌ی تونل فقط **TCP** را پشتیبانی می‌کند (UDP نه).
